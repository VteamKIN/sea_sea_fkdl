## User Requirements

- 创建一份可执行的排查与修复计划，定位“路径规划没有生效”的具体原因。
- 重点围绕路径决策链路中的关键变量与状态：`choose[]`、`dir_count`、`current_junction`、`junction_detected`、`road_type`。
- 计划需先找出真实失效点，再给出最小改动的修复路径与验证步骤。

## Product Overview

- 对现有双核运行流程中的“图像识别决策 → 控制执行”全链路进行核查。
- 输出可复现、可验证的结论：到底是路径配置语义冲突、路口判定不稳定、计步推进条件未触发，还是多因素叠加导致。

## Core Features

- 路径配置语义一致性核查（`choose`值与左转/右转/停车含义统一）。
- 路口识别到转向输出链路核查（`detect_junction_type` 到 `detect_road_type`）。
- 计步推进与边界保护核查（`dir_count`推进条件、越界与停机条件）。
- 屏显/串口观测验证，形成“现象-原因-修复”闭环。

## Tech Stack Selection

- 复用现有工程：TC264 C工程、CPU1图像处理与CPU0中断控制协作架构。
- 严格沿用当前工程约束：不改 `libraries/`，公共引用继续通过 `zf_common_headfile.h`，不引入新框架。

## Implementation Approach

- 采用“链路分段核对 + 运行期观测 + 最小修复”策略：先验证变量在每一段是否符合预期，再修正语义和状态推进逻辑。
- 核心决策点按调用顺序排查：`img_process()` → `detect_junction_type()` → `detect_road_type()` → `control_process()`。
- 重点技术决策：
- 先确认语义冲突（`choose`历史含义与当前实现是否一致）再改逻辑，避免误修。
- 修复优先级：语义统一 > 路口分支映射 > `dir_count`推进稳定性 > 防越界与安全停机。
- 性能与可靠性：
- 仅增加轻量观测点（整数显示/简短串口），时间复杂度保持 O(1) 级别，不改变主处理路径复杂度。
- 控制中断路径避免重型输出，防止干扰实时性。

## Implementation Notes (Execution Details)

- 以现有变量为主，不新增大范围状态机重构，控制改动爆炸半径。
- 所有调试观测先短期开关化，定位后可关闭，避免长期日志噪声。
- 保持向后兼容：默认行为不应影响非路径规划流程（如基础循迹与停车保护）。

## Architecture Design

- 当前有效链路关系：
- `code/img_process.c`：生成路口与方向决策信号（`current_junction`/`junction_detected`/`road_type`）。
- `code/control.c`：消耗决策信号并推进 `dir_count`、执行停车/控制输出。
- `user/isr.c`：周期调用 `control_process()`，决定控制实时生效。
- `user/cpu1_main.c` 与 `user/cpu0_main.c`：图像处理完成标志同步与调试观测。
